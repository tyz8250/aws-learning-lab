## 今日の自分の理解

### ping

自分のPCなどからGoogleのような宛先へ通信し、
応答が返ってくるかを確認するもの。

「相手まで通信できるか？」を調べるときに使える。

### TTL

最初は「パケットがどれくらい生きているか、
値が悪いと接続状態が悪いのでは？」と理解していた。

→ 少し修正。

TTLは通信品質の良し悪しを直接表す値ではない。

パケットがルーターを1つ通過するたびに値が1減り、
0になるとパケットは破棄される。

つまり、
「パケットがネットワーク上を永遠に回り続けることを防ぐ仕組み」。

### DNS

人間はWebサイトを見るときに
IPアドレスを直接入力することはほとんどない。

例：
google.com
↓
DNSに問い合わせる
↓
対応するIPアドレスを知る
↓
そのIPアドレスのサーバーへ通信する

DNS = Domain Name System

※「4セクション」というより、
IPv4アドレスは「.」で区切られた4つの数値で表現される。

### 冗長化

サーバーを複数用意しておき、
1台に障害が発生しても別のサーバーでサービスを継続できるようにする。

### ロードバランサー

複数のサーバーに対して
リクエストを適切に振り分ける役割。

冗長化したサーバーを
実際に活用するためにも重要。

### スケーラビリティ

アクセス量などに応じて、
処理能力を増減できる性質。

今の理解：
「必要に応じてサーバーを増やしたり減らしたりできる」

これは概ねOK。

ただし、
スケーラビリティ = 自動的に増減する仕組み
ではない。

自動で増減させる仕組みは
AWSではAuto Scalingなどが担当する。

## 今日つながったこと

Webサイトを見る流れが少し見えてきた。

さらにAWSでは、

ロードバランサーやAuto Scalingを使うことで
障害やアクセス増加に対応できる。

## 今日の理解

### 1. pingでgoogle.comに接続する場合

`google.com` はドメイン名なので、まずDNSで名前解決し、対応するIPアドレスを取得する。

その後、pingは取得したIPアドレス宛てに **ICMP Echo Request** を送る。相手から **ICMP Echo Reply** が返ってくると、応答時間やTTLなどを確認できる。

### 2. ブラウザでHTTPS接続する場合

ブラウザで `https://google.com` を開くと、まずDNSでIPアドレスを取得する。

その後、通常のHTTPS通信では、取得したIPアドレス宛てにTCP接続を確立する。続いてTLSハンドシェイクを行い、サーバー証明書の検証などを通じて暗号化通信を確立する。

その後、ブラウザがHTTPリクエストを送り、サーバーからHTTPレスポンスを受け取る。ブラウザはその内容を解析し、Webページを表示する。

## 理解の変化・修正

### pingの通信相手

- Before: pingはWebブラウザへリクエストを送ると思っていた
- After: pingは名前解決で得たIPアドレス宛てにICMP Echo Requestを送る。通信相手は宛先のホスト

### TTLとTLS

- Before: pingの結果としてTLSが返ってくると説明していた
- After: pingの結果に表示されるのはTTL。TLSはHTTPSなどで暗号化通信を確立するための仕組みで、別物

### 応答時間

- Before: 相手が応答時間を送ってくると思っていた
- After: `time` はpingを実行した側が測定する往復時間（RTT）

## 今日つながったこと

ping:
`ドメイン名 → DNS → IPアドレス → ICMP Echo Request → Echo Reply`

HTTPS:
`URL → DNS → IPアドレス → TCP接続 → TLSハンドシェイク → HTTPリクエスト → HTTPレスポンス → 画面表示`

DNSによる名前解決までは共通しているが、その後に使う仕組みが異なる。

## 今日追加で学んだこと

## NAT

NATは、IPアドレスを変換する仕組み。

例えば、プライベートIPアドレスを持つ端末がインターネットへ通信するときに、グローバルIPアドレスへ変換して通信できるようにする。

### 今日の理解

`プライベートIPアドレス ⇄ NAT ⇄ グローバルIPアドレス`

※ 家庭用ルーターなどでは、IPアドレスだけでなくポート番号も利用して複数端末の通信を区別する仕組み（NAPT/PAT）もよく使われる。

## ポート

ポート番号は、1台のコンピューターの中で「どのサービス・アプリケーション宛ての通信か」を区別するための番号。

ネットワーク通信における「ドア番号」のようなイメージ。

例：
- SSH：22番
- HTTP：80番
- HTTPS：443番
- 8080番：Webアプリなどでよく使われる代替HTTPポート

## 理解の修正

### localhostと8080

- Before：localhostは8080番ポートだと思っていた
- After：`localhost` は自分自身のコンピューターを指す名前であり、ポート番号ではない

例えば、

`http://localhost:8080`

であれば、

- `localhost` → 接続先（自分のPC）
- `8080` → 接続するポート番号

という意味になる。

localhostでは、アプリケーションが待ち受けていれば8080以外のポートも利用できる。

## 今日つながったこと

IPアドレス：
「どのコンピューターに届けるか」

ポート番号：
「そのコンピューターのどのサービスに届けるか」

NAT：
「プライベートIPアドレスとグローバルIPアドレスの間を変換する」

という役割の違いが少し見えてきた。

# AWS理解ログ 2026-09-08

## 今日触ったこと

- プロセス
- PID
- OSによるプロセス管理
- CPU・メモリなどの資源管理
- プロセス分離とセキュリティ
- DockerのPID namespaceとのつながり

## 今日の理解

### プロセスとは

プロセスとは、実行中のプログラムをOSが管理する単位。

例えばChromeやSlackを起動すると、それぞれ別のプロセスとしてOSに管理される。

OSは各プロセスにPIDという番号を付けて識別する。

### OSがプロセスを分けて管理する理由

最初は、アプリケーション同士を分離してセキュリティを担保するためだと考えていた。

これは理由の一つだが、それだけではない。

OSは複数のプログラムに対して、

- CPU
- メモリ
- その他のシステム資源

を適切に割り当てる必要がある。

プロセス単位で管理することで、複数のアプリケーションを同時に動かしやすくなる。

また、プロセスごとにメモリ空間などを分離することで、一つのアプリケーションの不具合や異常が、他のアプリケーションへ影響するのを抑えることができる。

## 理解の修正

### PIDの役割

- Before:
  PIDによってプロセス同士が混在しないようにしていると考えていた

- After:
  PIDは、OSがそれぞれのプロセスを識別するための番号。

プロセス同士の分離そのものは、PIDだけで実現しているわけではなく、仮想メモリなど別の仕組みも関わっている。

## わかりやすい言い換え

プロセスは、OSが「今動いているプログラム」を管理するための単位。

OSはそれぞれのプロセスにPIDを付け、CPUやメモリなどの資源を割り当てる。

プロセスを分けて管理することで、複数のアプリケーションを同時に動かせるだけでなく、一つのアプリの不具合が他のアプリへ影響するのを抑えることもできる。

## 今日つながったこと

以前Dockerで学んだPID namespaceの知識が、OSのプロセス管理の理解につながった。

通常のOSでもプロセスはPIDによって識別される。

DockerではさらにPID namespaceを使うことで、

「そのコンテナからどのプロセスが見えるか」

という範囲を分離している。

## 1. トランザクション

### 今日の理解

トランザクションは、関連する複数のデータベース処理を一つのまとまりとして扱う仕組み。

例えば、複数の更新処理がある場合、途中まで成功した状態で終わらせず、すべて成功したらコミットし、失敗した場合はロールバックして元の状態に戻す。

### 理解の修正

- Before:
  完全に成功した際にも、ロックなどを使って他のユーザーが同時に更新しないようにする必要があると考えていた。

- After:
  トランザクションには、複数の処理を「すべて成功するか、失敗したら元に戻すか」という単位で扱う役割がある。

  一方、複数のユーザーが同時に操作する場合の整合性は、トランザクションの分離性やロックなどの仕組みで制御する。

  ロックは「他のユーザーの更新をすべて禁止する仕組み」ではなく、必要なデータへの同時アクセスを制御するための仕組み。

### 今日つながったこと

トランザクション：
「複数の処理を一つのまとまりとして扱う」

コミット：
「処理を確定する」

ロールバック：
「処理を取り消して元に戻す」

ロック：
「同時アクセスによる競合を制御する」

## 2. AWS VPCとサブネット

### 今日の理解

VPCは、AWS上に作成する仮想ネットワーク。

その中をサブネットに分割し、EC2などのリソースを配置する。

### 理解の修正

#### VPCとプロジェクト

- Before:
  一つのプロジェクトに一つのVPCがあると考えていた。

- After:
  一つのプロジェクトで一つのVPCを使う構成はあるが、必ずそうなるわけではない。

  要件に応じて、一つのVPCに複数のシステムを配置したり、一つのシステムで複数のVPCを使ったりすることもある。

#### パブリック／プライベートサブネット

- Before:
  サブネットの中にパブリックアドレス、プライベートアドレスを作ると考えていた。

- After:
  サブネットは、VPCのIPアドレス範囲を分割したネットワーク。

  パブリックサブネットとプライベートサブネットの違いは、主にルートテーブルによる通信経路。

  パブリックサブネット：
  インターネットゲートウェイへのルートを持つサブネット。

  プライベートサブネット：
  インターネットゲートウェイへの直接のルートを持たないサブネット。

  ※ パブリックサブネットに配置しただけで、EC2が自動的にインターネットからアクセス可能になるわけではない。パブリックIPアドレスやセキュリティグループなどの設定も関係する。

## 3. サブネットで使えるIPアドレス

### 今日の理解

AWSでは、サブネット内のIPアドレスのうち、一部がAWSによって予約されている。

例えば、IPv4の /24 サブネットの場合：

256個のIPアドレス

- AWS予約分 5個
= 利用可能 251個

### 補足

AWSでは、各サブネットの最初の4個と最後の1個のIPv4アドレスが予約される。

例えば 10.0.0.0/24 なら：

- 10.0.0.0：ネットワークアドレス
- 10.0.0.1：VPCルーター用
- 10.0.0.2：DNS用
- 10.0.0.3：AWSが将来の利用のために予約
- 10.0.0.255：予約アドレス

そのため、EC2などに割り当てられるのは251個。

## 今日つながったこと

VPC
  ↓
サブネットに分割
  ↓
EC2などを配置
  ↓
ルートテーブルで通信経路を制御
  ↓
必要に応じてインターネットへ接続

また、データベースでは、複数の更新を安全に扱うためにトランザクションやロックなどの仕組みがあることを理解した。
