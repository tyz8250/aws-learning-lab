## 今日の理解

TCPは、UDPと違って通信の信頼性を重視するプロトコル。

そのため、いきなりアプリケーションデータを送るのではなく、最初に **3-way handshake** を行い、クライアントとサーバーの間で通信を開始できる状態を作る。

## 3-way handshake

### 1. クライアント → サーバー

クライアントが、

「接続したい」

という意味で **SYN** を送る。

このとき、クライアント側の初期シーケンス番号も送る。

`Client → Server : SYN`

### 2. サーバー → クライアント

サーバーは、

「接続要求を受け取った。こちらも通信できる」

という意味で **SYN + ACK** を返す。

このとき、サーバー側の初期シーケンス番号も送る。

`Client ← Server : SYN + ACK`

### 3. クライアント → サーバー

クライアントが、

「サーバーからの返答を受け取った」

という意味で **ACK** を送る。

`Client → Server : ACK`

ここまで完了すると、TCP接続が確立され、その後データ通信が始まる。

## 理解の修正

### SYN1 / ACK1について

- Before:
  `SYN1` や `ACK1` というものを送ると考えていた

- After:
  SYNとACKは、TCPヘッダーにある制御用のフラグ。

  実際には、それとは別にシーケンス番号やACK番号が使われる。

概念としては、

`SYN → SYN + ACK → ACK`

と覚える。

## 大事な補足

3-way handshakeだけでTCPの信頼性が実現されているわけではない。

TCPでは、その後の通信でも、

- シーケンス番号
- ACK
- 再送
- 順序制御

などを使って、データを正しく届ける仕組みを持っている。

3-way handshakeは、その通信を始めるための接続確立の処理。

# AWS理解ログ 2026-09-15

## 今日触ったこと

- 親プロセス・子プロセス
- ターミナルとプロセスの関係
- SIGHUP
- 常駐プロセス
- Webサーバーをターミナルから切り離して動かす考え方

## 今日の理解

ターミナルからWebサーバーなどのプロセスを起動した場合、そのプロセスはターミナルのセッションに紐づいて動いていることがある。

そのため、ターミナルを閉じたときに、起動していたWebサーバーまで終了する場合がある。

最初は、

「ターミナルが親プロセスで、Webサーバーが子プロセスだから、親が消えると子も消える」

というイメージで理解していた。

これは方向性としては近いが、実際には親子関係だけではなく、ターミナルのセッションやシグナルも関係している。

## SIGHUP

ターミナルやSSH接続が切断されたとき、関連するプロセスに `SIGHUP` というシグナルが送られることがある。

プロセスがSIGHUPを受け取って終了する動作になっている場合、

`ターミナルを閉じる`
↓
`SIGHUPを受け取る`
↓
`プロセスが終了する`

という流れになる。

つまり、

`親プロセスが終了したから必ず子プロセスも終了する`

というより、

`ターミナルとの接続が切れたことでシグナルを受け取り、プロセスが終了する場合がある`

と考える方が正確。

## 常駐プロセス

Webサーバーのように、ターミナルを閉じても動き続けてほしいプログラムは、ターミナルとは独立して動かす必要がある。

このように、バックグラウンドで継続して動作するプロセスを常駐プロセスとして管理する。

Linuxでは、Webサーバーなどを `systemd` のような仕組みでサービスとして管理することが多い。

例えば、

`ターミナル`
↓
`systemctl start nginx`
↓
`systemdがnginxを管理`

という形にすると、ターミナルを閉じてもnginxは動作し続ける。

## 理解の修正

### Before

ターミナルが親プロセスで、Webサーバーが子プロセスとして紐づいているため、ターミナルを閉じるとWebサーバーも終了すると考えていた。

### After

親子関係だけではなく、ターミナルのセッションやSIGHUPなどのシグナルが関係する。

ターミナルを閉じても動かしたいプロセスは、ターミナルから切り離し、systemdなどの仕組みで常駐プロセスとして管理する。

## 今日つながったこと

以前学んだ、

- プロセス
- PID
- 親プロセス・子プロセス
- systemctl

が、Webサーバーの運用とつながってきた。

AWSのEC2上でWebサーバーを動かす場合も、

`SSHで接続`
↓
`Webサーバー起動`
↓
`SSHを切断`

してもサービスを継続する必要がある。

そのため、単純にターミナル上でプログラムを実行するのではなく、サービスとして常駐させる考え方が重要。

## まだ曖昧

- SIGHUPが具体的に誰から誰へ送られるのか
- `nohup` と `systemd` の違い
- バックグラウンド実行 `&` だけではなぜ不十分な場合があるのか
- デーモンと常駐プロセスの違い

## 次につなげること

「なぜSSHを切断してもWebサーバーは動き続けるのか」

を、自分の言葉で説明できるようにする。

# AWS理解ログ 2026-09-16

## 今日触ったこと
- データベースの同時更新
- トランザクション
- ロック
- 在庫更新の競合

## 今日の理解

例えば、在庫が1個しかない商品を2人が同時に購入しようとすると、両方が「在庫あり」と判断してしまい、2人とも購入できてしまう可能性がある。

このような同時更新による競合を防ぐために、データベースではトランザクションやロックを使う。

## 在庫1個の商品を2人が購入する場合

例えば在庫数が1の商品に対して、

- ユーザーA
- ユーザーB

が同時に購入処理を行うとする。

ユーザーAが先に対象データを更新する処理に入り、そのデータに対して適切なロックがかかると、ユーザーBは同じデータを同時に更新できない状態になる。

ユーザーAのトランザクションが終了したあと、ユーザーBの処理が進む。

その時点で在庫が0になっていれば、ユーザーBは購入できない。

## 理解の修正

### Before

「1人の処理が終わるまでデータベース全体をロックする」

ようなイメージを持っていた。

### After

実際には、必要なデータに対して適切な範囲でロックを行う。

例えば商品1件の更新であれば、その商品の行などを対象にロックする考え方がある。

データベース全体をロックすると、他の関係ない処理まで止まってしまうため、ロックの範囲は重要。

## トランザクションとロックの役割

### トランザクション

複数の処理を一つのまとまりとして扱う。

成功すればコミットし、失敗すればロールバックする。

### ロック

複数の処理が同じデータを同時に変更して、矛盾した状態になるのを防ぐ。

つまり、

`トランザクション = 処理のまとまり`

`ロック = 同時更新の競合を防ぐ仕組み`

と分けて考える。

## 今日つながったこと

在庫1個の商品を2人が購入する例では、

1. ユーザーAが購入処理を開始
2. 対象の在庫データをロック
3. 在庫を確認・更新
4. コミット
5. ロック解除
6. ユーザーBが処理を進める
7. 在庫0を確認
8. 購入不可と判断

という流れで、二重購入を防ぐことができる。
